02

执行流水线

LangGraph StateGraph 用 add_edge 顺序串联 6 个节点；analysis 与 review 两个节点内部各自以 2 线程并行调度专家。

解析阶段 抽取阶段 调度 / 成文 分析组 评审组

extract 不是 ReAct 循环

它直接调用 extract_fields(source_text, client, max_chars=40000, on_delta) 再 compute_metrics()，只借用事件协议对外表现为一个智能体（payload.agent="extractor"）。前端窗口一致，但省掉多轮 ReAct 开销。

coordinator 是确定性的

计划来自模块级常量 COORDINATOR_PLAN + REVIEW_PLAN，不调用 LLM。主管的"调度决策"被固化为流程设计，换来确定性与零 Token 消耗。

并行为什么要队列

LangGraph 的 get_stream_writer() 绑定 runnable context，子线程直接调用会抛 Called get_config outside of a runnable context。改用 queue.Queue 中转，主线程每 80ms 轮询 drain。

三层抽象：Tool · Skill · Agent

与主流开源 Agent 底座一致的范式组织。三者通过 core/registry.py 单一注册表解耦。

Tool · 原子能力

Python 函数，模型可直接调用，无决策能力。通过 input_schema 简化格式声明参数，json_schema() 实时转换为标准 JSON Schema，供 OpenAI tools 参数与 MCP 客户端复用。

inject 机制：{"client", "on_delta"} 这类运行时依赖不出现在模型参数列表里，由执行器按声明注入。

backend/app/tools/ · 23 个已注册

Markdown 文件 + YAML frontmatter，描述"这类任务该怎么做"。用文件而非函数，是因为核心价值是流程知识而非能力——让金融背景的队友也能参与编写迭代，不必改代码。

技能为什么内联而不运行时加载

代码注释写得很清楚：① 省去每个智能体一轮 load_skill 调用；② 让技能正文成为稳定的 prompt 前缀，命中 API 的自动缓存。因此 build_system_prompt 刻意不拼接时间戳、随机数等易变内容——system prompt 必须逐字稳定，任何变动都会导致缓存失效。

04

端到端数据流

从用户点击运行到结果渲染的完整链路。凭据全程走 HTTP 请求头，不进 URL 与表单。

为什么凭据必须走请求头

代码注释点明了原因：uvicorn 的 access log 会记录完整请求行（含查询串）。把 Key 放 URL 会导致密钥明文出现在日志、浏览器历史与代理记录三处。请求头不在默认日志范围内。代价是 CORS 必须把 9 个头显式列进 allow_headers（Content-Type + 5 个 X-LLM-* + 3 个 X-Search-*），否则浏览器预检会拒绝。

为什么一次 astream 拿两样

astream(..., stream_mode=["custom","values"]) 一次执行同时返回实时事件与最终状态，避免了「先跑一遍拿事件、再跑一遍拿状态」的重复执行——重复执行意味着双倍 Token。

状态传递的三个通道

通道载体用途
事件通道queue.Queue → emit → SSE实时展示，不参与计算。子线程写入、主线程抬升
artifacts 通道AgentRunner 返回的 artifacts 字典结构化产物，供编排器按工具名映射提取到 state
检查点通道checkpoint.save / load跨进程持久化 + 断点续跑，节点级 + 专家级双层缓存
◆
列表字段用 operator.add 归约

InvestState 中 trace 与 errors 声明为 Annotated[list, operator.add]，使并行的专家节点各自追加而不互相覆盖；其余字段用 total=False 声明为可选，避免并行节点覆盖未设置的键。

05

ReAct 执行器内部循环

使用原生 function calling：工具声明为 OpenAI 格式的 tools 参数，模型返回结构化 tool_calls，全程不需要任何文本解析。

终止条件（进展检测为主 + 防御性硬上限）

条件行为
模型未返回 tool_calls 且正文非空正常收敛 —— 正文即最终结论，跳出循环
完全空输出且连续 3 步判定停滞，用历史最长正文 best_body 收尾
有工具调用视为有进展，停滞计数清零，继续下一轮
触及 max_steps（默认 24）防御性硬上限，强制收尾并置 truncated: true
✓
为什么保留 max_steps

终止以进展检测为主（模型未返回 tool_calls 且正文非空，或连续多步无进展），常规任务不会触顶——这避免了长任务（如多次调整估值假设）被腰斩。但进展检测把「有工具调用」一律视为有进展，模型若稳定地反复调用工具就能无限跑，因此保留 max_steps（DEFAULT_MAX_STEPS = 24）作为纯防御性硬上限：触顶后强制收尾，并在 agent_end.payload 置 truncated: true 透出到前端。

为什么写 JSONL 不写 JSON 数组

流式追加写入，不需要在内存里累积；进程崩溃时已写入的内容仍然可读。对需要长跑的 Agent 流程，这是关键的容错属性。

为什么写入要原子替换

先写 .tmp 再 replace()，避免进程在写入中途被杀时留下半截 JSON——那会导致 load() 解析失败，检查点直接作废。

敏感信息递归脱敏

SENSITIVE_KEYS = {"api_key","apikey","authorization","token","secret"}，对嵌套 dict / list 递归处理，任何层级出现这些键名都替换为 ***。单条 message 截断到 2000 字。

断点续跑的两层缓存

节点级

节点开头查 ckpt["completed_nodes"] 与产出字段，命中则直接返回缓存值并发出 resumed: True 事件。恢复入口目前只在接口层（GET /api/runs/latest + GET /api/analyze/resume），前端 hook 已实现但界面未挂按钮。后者靠 checkpoint.latest() 按 mtime 倒序找第一个未完成记录。

专家级（更细）

_run_group 读取 ckpt["agents"][key]，有 output 就直接复用，只发 agent_start + agent_end 两个 resumed 事件——完全不消耗 Token。且每个专家完成即落盘，中断损失最小。
